import { Tabs, TabItem } from '@astrojs/starlight/components';

Honker's pub/sub is a direct analog of Postgres's `pg_notify` / `LISTEN`: fire-and-forget signals between processes that share a SQLite file. The Python binding measured 2.9 ms p50 cross-process wake latency on an Apple M1 Pro over 500 samples. No replay, no delivery guarantees. For that, use [Streams](/guides/streams/).

The wire format is the same across bindings: a Python publisher and a Go listener talk to the same channel through the same `.db` file.

## Listen

The listener starts from `MAX(id)` at attach time. Historical notifications are not replayed. Honker runs a shared commit-poll thread at 1 ms cadence (one `PRAGMA data_version` read per database, counter increments on every commit from any connection in any journal mode), so every listener in the process wakes on any commit and then filters by channel at the `SELECT` level.

Ruby and Elixir currently expose `notify` plus `wait_for_update`, but not a high-level channel listener. In those bindings, snapshot `MAX(id)` when attaching, wait for database updates, and query `_honker_notifications` for newer rows on the desired channel. See [Binding support](/reference/bindings/) for the API-shape distinction.

## Cross-process

The commit watcher fires on commits from *any* process. A FastAPI app, a CLI worker, and a cron job can all `notify()` the same channel, and a separate listener receives every signal within a few milliseconds. No coordination, no broker, no extra network hop.

## Pruning

Notifications accumulate in `_honker_notifications` until you prune them. There's no auto-prune because "how much history do you want" is a product decision.

| Binding | Typed age pruning | Typed max-count pruning |
| --- | ---: | ---: |
| Python, Node, Rust, .NET, Java, Kotlin | yes | yes |
| Ruby, Elixir | yes | no |
| Go, Bun, C++ | no | no |

Every binding can use the raw-SQL fallback below.

```python
# Python
db.prune_notifications(older_than_s=3600)   # delete rows older than 1 hour
db.prune_notifications(max_keep=10_000)     # keep only the most recent 10k
```

```js
// Node
db.pruneNotifications(3600);        // delete rows older than 1 hour
db.pruneNotifications(null, 10000); // keep only the most recent 10k
```

```csharp
// .NET
db.PruneNotifications(olderThanSeconds: 3600);
db.PruneNotifications(maxKeep: 10_000);
```

```java
// Java (Kotlin uses the same JVM API or notificationPruneOptions { ... })
db.pruneNotifications(NotificationPruneOptions.builder()
    .olderThan(Duration.ofHours(1))
    .maxKeep(10_000)
    .build());
```

There are no `honker_prune_*` SQL functions — pruning is a binding-level helper. From raw SQL, delete against the table directly:

```sql
DELETE FROM _honker_notifications WHERE created_at < unixepoch() - 3600;
```
