## Install

```bash
cargo add honker
```

Enable experimental watcher backends when you need them:

```toml
honker = { version = "0.4", features = ["kernel-watcher", "shm-fast-path"] }
```

## Open

```rust
use honker::Database;

let db = Database::open("app.db")?;
```

The default polling watcher backend needs no extra features. To opt into the
experimental `shm` or `kernel` backends, enable the Cargo features above and
open with `OpenOptions::default().watcher_backend("shm")?` passed to
`Database::open_with_options` — an explicit request for a backend whose feature
isn't compiled in fails instead of silently falling back.

The Rust binding registers Honker functions directly through `honker-core`; it
does not need to load a `.so` / `.dylib` at runtime.

## Queue

```rust
use honker::{EnqueueOpts, QueueOpts};
use serde_json::json;

let q = db.queue("emails", QueueOpts::default());
q.enqueue(&json!({"to": "alice@example.com"}), EnqueueOpts::default())?;

if let Some(job) = q.claim_one("worker-1")? {
    job.ack()?;
}
```

## Job details and typed payloads

A claimed `Job` and a `JobRow` snapshot from `get_job` both carry the
[twelve job fields](/guides/queues/#job-fields) under the core's own
`snake_case` names — no renaming.

`Database::typed_queue::<T>` gives you a `Queue<T>`, and the type flows into
`enqueue`, `claim_one`, `claim_batch`, and `get_job`:

```rust
use honker::{Database, EnqueueOpts, QueueOpts};
use serde::{Deserialize, Serialize};

#[derive(Serialize, Deserialize)]
struct Email {
    recipient: String,
}

let db = Database::open("app.db")?;
let emails = db.typed_queue::<Email>("emails", QueueOpts::default());

let id = emails.enqueue(&Email { recipient: "alice@example.com".into() }, EnqueueOpts::default())?;

if let Some(job) = emails.claim_one("worker-1")? {
    let email: Email = job.payload_typed()?;
    println!("{} attempt {}/{}", email.recipient, job.attempts, job.max_attempts);
    job.ack()?;
}
```

Rust does not decode the payload for you. A claimed `Job` holds `payload:
Vec<u8>` and a `JobRow` holds `payload: String`; both offer `payload_typed()`
for the queue's `T`, and `payload_as::<U>()` when you want a different type at
one call site:

```rust
if let Some(row) = emails.get_job(id)? {
    // row.worker_id and row.claim_expires_at are None while pending.
    let email: Email = row.payload_typed()?;
}
```

On a claimed `Job`, `worker_id` and `claim_expires_at` are plain values — a
claim guarantees both. On a `JobRow` they are `Option`, along with
`expires_at`.

The type parameter is a compile-time convenience. honker never validates
payload shape at runtime; a mismatch surfaces as a `serde` error when you call
`payload_typed()`.

## Transactional Outbox

```rust
let outbox = db.outbox("email", Default::default());

let tx = db.transaction()?;
tx.execute("INSERT INTO orders (id, total) VALUES (?1, ?2)", (42, 9900))?;
outbox.enqueue_tx(&tx, &json!({"order_id": 42}), Default::default())?;
tx.commit()?;
```

Run delivery workers in a separate process so crashes and restarts preserve the
same database-backed retry semantics.

## ORM Section

For new Rust apps, prefer the native `honker` crate. For existing `sqlx`
SQLite apps, load the Honker extension on the same pool connection and execute
`honker_*` SQL inside the `sqlx::Transaction`.

See the full [Rust ORM recipe](/guides/orm/rust/) for `sqlx` wiring and the
tradeoff between native `rusqlite` wrappers and ORM-owned connections.

## Testing

Use `tempfile::tempdir()` plus a real `.db` path. If you are testing `shm`,
keep a connection open while subprocess workers run so SQLite's WAL-index file
does not disappear between process opens.
