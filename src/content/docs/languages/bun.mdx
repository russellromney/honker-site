## Install

```bash
bun add @russellthehippo/honker-bun
```

Bun loads the Honker SQLite extension through `bun:sqlite`, so keep
`libhonker_ext.{so,dylib,dll}` next to your app or configure an absolute path.

## Open

```ts
import { open } from "@russellthehippo/honker-bun";

const db = open("app.db", "./libhonker_ext.dylib");
```

The default polling watcher backend is always available. `open(..., { watcherBackend: "shm" })`
or `"kernel"` opts into the experimental backends — they throw unless the loaded
extension was built with the matching Cargo features (official release artifacts
have them; source builds per these docs don't).

## Queue

```ts
const q = db.queue("emails");
q.enqueue({ to: "alice@example.com" });

const job = q.claimOne("worker-1");
if (job) {
  await sendEmail(job.payload);
  job.ack();
}
```

## Job details and typed payloads

A claimed job and a `getJob` snapshot both carry the
[twelve job fields](/guides/queues/#job-fields), renamed to camelCase
(`runAt`, `workerId`, `claimExpiresAt`, `maxAttempts`, `createdAt`,
`expiresAt`).

`db.queue<T>(name)` returns a `Queue<T>`, and the payload type flows into
`enqueue`, `claimOne`, `claimBatch`, and the claim waker:

```ts
import { open, type Job, type JobSnapshot } from "@russellthehippo/honker-bun";

interface EmailPayload {
  recipient: string;
  template: "welcome" | "receipt";
}

const db = open("app.db", "./libhonker_ext.dylib");
const emails = db.queue<EmailPayload>("emails");

const id = emails.enqueue({ recipient: "alice@example.com", template: "welcome" });

const job: Job<EmailPayload> | null = emails.claimOne("worker-1");
if (job) {
  console.log(job.payload.recipient, job.attempts, "/", job.maxAttempts);
  job.ack();
}
```

`getJob` is the one place the type does **not** flow: it returns a plain
`JobSnapshot` whose `payload` is the raw JSON text. Decode it yourself:

```ts
const snapshot: JobSnapshot | null = emails.getJob(id);
if (snapshot) {
  const payload = JSON.parse(snapshot.payload) as EmailPayload;
  // snapshot.workerId and snapshot.claimExpiresAt are null while pending.
}
```

The type parameter is a TypeScript contract only. honker never validates
payload shape at runtime.

## Transactional Outbox

```ts
const outbox = db.outbox("email", async (payload) => sendEmail(payload));

const tx = db.transaction();
try {
  tx.execute("INSERT INTO orders (id, total) VALUES (?, ?)", [42, 9900]);
  outbox.enqueueTx(tx, { orderId: 42 });
  tx.commit();
} catch (error) {
  tx.rollback();
  throw error;
}

await outbox.runWorker("email-worker");
```

## ORM Section

For Drizzle or other TypeScript layers over `bun:sqlite`, load the extension on
the same `Database` connection and execute Honker SQL inside the same
transaction as your business write. If an ORM hides the underlying connection,
move enqueue-critical writes into an explicit `bun:sqlite` transaction.

See the [JavaScript / TypeScript ORM recipe](/guides/orm/javascript/) for the
shared Node/Bun approach.

## Testing

Use file-backed temp databases and `Bun.spawn` workers for queue/outbox
watcher proofs. That catches extension load and wake behavior outside one Bun
process.
