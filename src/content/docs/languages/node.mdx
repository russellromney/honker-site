## Install

```bash
npm install @russellthehippo/honker-node
```

The package ships a native `.node` binding for supported release targets.

## Open

```js
const honker = require("@russellthehippo/honker-node");

const db = honker.open("app.db", undefined, "shm");
```

The third argument selects the watcher backend. Use `undefined` or `"polling"`
for the stable default, `"kernel"` for filesystem wake hints, or `"shm"` for
the WAL-index fast path.

## Queue

```js
const q = db.queue("emails");
q.enqueue({ to: "alice@example.com", orderId: 42 });

const job = q.claimOne("worker-1");
if (job) {
  await sendEmail(job.payload);
  job.ack();
}
```

## Job details and typed payloads

A claimed job and a `getJob` snapshot both carry the
[twelve job fields](/guides/queues/#job-fields), renamed to camelCase
(`runAt`, `workerId`, `claimExpiresAt`, `maxAttempts`, `createdAt`,
`expiresAt`).

`db.queue<T>(name)` returns a `Queue<T>`, and the payload type flows into
`enqueue`, `claimOne`, `claimBatch`, `claimWaker`, and `getJob`:

```ts
import { open, type Job, type JobSnapshot } from "@russellthehippo/honker-node";

interface EmailPayload {
  recipient: string;
  template: "welcome" | "receipt";
}

const db = open("app.db");
const emails = db.queue<EmailPayload>("emails");

const id = emails.enqueue({ recipient: "alice@example.com", template: "welcome" });

const job: Job<EmailPayload> | null = emails.claimOne("worker-1");
if (job) {
  console.log(job.payload.recipient, job.attempts, "/", job.maxAttempts);
  job.ack();
}

const snapshot: JobSnapshot<EmailPayload> | null = emails.getJob(id);
// snapshot.state is "pending" | "processing"; workerId and claimExpiresAt are
// null while the job is pending.
```

Node decodes the payload on both paths — a claimed `job.payload` and a
`getJob` snapshot's `payload` are both already-parsed values.

The type parameter is a TypeScript contract only. honker never validates
payload shape at runtime, so every producer writing to `emails` has to agree on
`EmailPayload` by itself.

## Transactional Outbox

```js
const outbox = db.outbox("email", async (payload) => {
  await sendEmail(payload);
});

const tx = db.transaction();
try {
  tx.execute("INSERT INTO orders (id, total) VALUES (?, ?)", [42, 9900]);
  outbox.enqueueTx(tx, { orderId: 42 });
  tx.commit();
} catch (error) {
  tx.rollback();
  throw error;
}

await outbox.runWorker("email-worker");
```

Outbox jobs retry with backoff when delivery throws.

## ORM Section

For `better-sqlite3`, Drizzle, or Kysely-on-SQLite, load the Honker extension
on the connection your ORM uses and run Honker SQL inside the ORM transaction.
Prisma owns its SQLite connection more tightly, so the fully atomic path is to
put the enqueue-critical write in a small explicit SQLite transaction outside
Prisma or accept that a second Honker connection is not atomic with Prisma's
write.

See the full [JavaScript / TypeScript ORM recipe](/guides/orm/javascript/) for
Drizzle, Kysely, and Prisma-adjacent patterns.

## Testing

Use Node's test runner with a temporary file-backed database and spawn worker
processes for queue/outbox proofs. That catches native extension loading and
watcher behavior in the same shape production uses.
